## Problem Statement

Beginners running local LLMs on Apple Silicon often find a model on Hugging Face, then search for somebody else's MLX quantization. If the desired quantization does not exist, they must either wait for an upload or learn a manual conversion workflow. A beginner with a 32 GB MacBook who wants to run a model such as Qwen3 27B should be able to provide the original Hugging Face model ID and get a safe, verified local MLX model without guessing at bit-widths, memory requirements, or model support.

## What Makes This Cool

The useful moment is: give `mlx-autoquant` any suitable Hugging Face model, see what will fit on the current Mac before downloading the large weight files, then receive a verified runnable MLX package and a report explaining the decision. The tool removes the need to browse for pre-quantized uploads or understand the conversion pipeline first.

## Constraints

- The first user is a beginner trying local LLMs on a constrained Apple Silicon machine, with 32 GB unified memory as the concrete example.
- The primary workflow is one command from model ID to verified output.
- The tool must inspect metadata and report an estimated plan before downloading model weights.
- Automatic selection means the highest tested precision predicted to fit safely, not measured fastest runtime in the first release.
- Unsupported or risky architectures should be identified before a large download when the available metadata allows it.
- Existing `mlx_lm.convert` remains the conversion engine; this project should not fork MLX conversion behavior.
- Apple Silicon is the supported runtime. The existing PyPI package, GitHub Actions CI, and tag-driven PyPI release remain the distribution path.
- The first release is limited to text-generation Transformers checkpoints that the installed `mlx-lm` version supports without custom conversion code; it is not a universal multimodal or arbitrary-model converter.
- Preflight must distinguish inference memory from temporary conversion disk space and must fail early when either requirement cannot be estimated safely.
- Automatic conversion pauses after preflight; `--yes` is the explicit automation escape hatch and the preflight result is still printed or emitted as JSON.

## Premises

1. The main problem is decision uncertainty, not the absence of a model conversion API.
2. A trustworthy workflow needs explicit stages: metadata preflight, decision, conversion, verification, and reporting.
3. The decision policy should be separate from CLI argument parsing and MLX execution so it can later support measured benchmarks and other frontends.
4. Memory estimates are useful only when their assumptions are visible, conservative, and recorded in the report.
5. “Any Hugging Face model” must be narrowed to models supported by the underlying Transformers and MLX conversion paths; unsupported models should fail early with actionable diagnostics.

## Approaches Considered

### Approach A: Verified One-Command Path

Strengthen the current CLI and planner with early support checks, an explicit preflight summary, conversion, verification, and a beginner-readable report. This is the smallest release and reuses the current modules directly.

Rejected for now because it leaves policy embedded in the current flow and makes future benchmark-driven choices harder to add cleanly.

### Approach B: Quantization Decision Engine

Introduce a distinct planning layer that represents hardware, model metadata, supported architectures, memory budgets, quantization candidates, and decision evidence. The CLI becomes an adapter over explicit stages: preflight, choose, convert, verify, and report. Benchmark results can become another decision input later without changing the beginner workflow.

Chosen because it gives the project a long-term home for explainable quantization policy while keeping the first user experience focused on one-command conversion.

### Approach C: Reproducible Model Build Artifact

Treat each conversion as a build with a pinned Hub revision, hardware snapshot, selected plan, output checksums, verification result, and exact command. Add commands to inspect and reproduce builds.

Deferred because reproducibility is valuable for contributors, but the first release must first make the beginner's initial conversion reliable and understandable.

## Recommended Approach

Build the Quantization Decision Engine around five explicit stages:

1. **Preflight** fetches only lightweight model metadata, profiles the architecture, detects hardware, computes context and memory assumptions, and checks whether the model is eligible for conversion.
2. **Decision** evaluates supported quantization candidates and returns a structured decision containing the selected precision, alternatives, fit status, assumptions, warnings, and rationale. The existing highest-fitting-precision policy remains the first implementation.
3. **Conversion** runs only after preflight succeeds and writes into an empty output directory. It consumes the decision rather than recomputing policy inside the CLI.
4. **Verification** loads the generated model, performs a short generation smoke test, records generated tokens and peak memory when available, and reports failures as conversion failures rather than silent partial success.
5. **Reporting** writes a stable JSON report and a concise terminal summary. The report includes source model and revision, hardware, architecture support result, selected and rejected candidates, memory assumptions, conversion settings, verification result, and warnings.

The first release should also expose a machine-readable preflight result for scripts and future frontends. Human output should make the important boundary obvious: metadata inspection is cheap; weight download and conversion are the expensive step. The CLI should not silently download the large checkpoint after a dry-run-style failure or an unsupported-model warning.

### Stage Contracts

| Stage | Input | Output | Failure behavior |
| --- | --- | --- | --- |
| Preflight | Model ID, requested revision, hardware snapshot, context length | `PreflightResult` with resolved immutable revision, metadata provenance, compatibility result, estimated inference memory, estimated temporary disk, and warnings | No weight download. Return an actionable error for missing metadata, authentication, network, disk, or unsupported architecture. |
| Decision | `PreflightResult`, optional user bit-width, policy version | `QuantizationDecision` with candidates, selected plan, fit evidence, assumptions, and warnings | Automatic selection chooses the highest fitting candidate. A forced `--bits` value is accepted only when it fits the same budget; no unsafe override exists in the first release. |
| Conversion | Approved `QuantizationDecision`, source revision, output path | `ConversionResult` with output path, downloaded bytes, duration, and conversion settings | Preserve a diagnostic report and clean incomplete model files by default; never present a partial output as successful. |
| Verification | Completed output path, tokenizer, verification settings | Existing `VerificationResult` extended with load status, generated output, token count, and peak memory when available | Mark the report failed and return non-zero if loading or generation fails or produces empty output. |
| Reporting | All stage results, including partial failures | Versioned `autoquant-report.json` plus terminal summary | Write a diagnostic report for failures when the output directory is available. Report-writing failure is a command failure; the model is not described as verified if the report cannot be written. |

The stage objects are internal Python contracts in the first release, not a public plugin API. Required fields are: `PreflightResult` has model ID, requested revision, resolved commit SHA, architecture, metadata provenance, compatibility, warnings, source weight bytes, estimated inference bytes, estimated temporary bytes, and available disk; `QuantizationDecision` has policy version, candidates, selected settings, fit evidence, assumptions, and forced-selection status; `ConversionResult` has source commit SHA, output path, downloaded bytes, duration, and cleanup status; `VerificationResult` has load status, generation status, generated text, token count, and peak memory; the report has `schema_version: 1` plus all stage results. Stage failures use typed categories for authentication, network, metadata, unsupported model, insufficient memory, insufficient disk, conversion, verification, cancellation, and reporting.

The resolved Hub commit SHA is passed to every metadata fetch, weight download, and conversion operation. If the installed `mlx_lm.convert` API cannot accept a revision directly, the adapter passes a local snapshot directory containing only the pinned revision and records that fallback. Preflight may inspect `config.json`, tokenizer metadata, and safetensors index metadata, but never downloads tensor shards. Disk accounting uses `source_weight_bytes + estimated_output_bytes + required_metadata_bytes` as the conversion footprint, then applies the 15% allowance to that combined footprint. It compares that total plus existing output contents against free space at both cache and output locations, counting cached files only when they match the resolved SHA. Unknown required sizes stop automatic conversion instead of producing a false fit result. Conversion downloads required model and tokenizer files, not documentation or unrelated repository files.

Conversion cancellation and failure preserve a diagnostic report and remove incomplete tensor output by default. A failed run leaves the report in a sibling diagnostic location or recreates an empty output directory before retry; rerunning never consumes partial tensors. The existing `--no-verify` flag remains as an expert/debug escape hatch, but the report marks verification skipped, prints a warning, and the output is never described as verified. A normal automatic run always verifies.

The decision engine should preserve the current planner's conservative assumptions while making them data rather than hidden constants: KV-cache estimate, system reserve, conversion/sharding allowance, context length, and parameter-count provenance. The first-release defaults are a maximum context of 8192 tokens unless overridden, fp16 K/V values, a system reserve of `max(4 GiB, 25% of unified memory)`, and a 15% weight-estimate allowance. Quantized output size uses the current packed-weight plus scale/bias-per-group formula with group size 64. A plan based on safetensors metadata must say so; a config-derived estimate must say it is an estimate.

Model support should be represented as an explicit compatibility result with at least: supported, unsupported, and needs-review states. The first implementation can derive this from known configuration fields and the underlying conversion capability, but it must avoid claiming universal support. Each unsupported result should identify the architecture or missing metadata and suggest the next action, such as trying a supported checkpoint or filing a model-support issue.

For the first release, the support matrix covers causal text-generation checkpoints represented by the architecture families exercised by the installed `mlx-lm` conversion API and the repository's fixtures. It must include the current tiny Llama fixture plus a pinned small Qwen-family causal checkpoint, selected to exercise the Qwen config path without requiring Qwen3 27B-sized weights, before claiming Qwen support. If full Qwen conversion exceeds normal PR limits, it runs in scheduled or release CI while mocked preflight coverage runs on every PR. A family is `supported` only when metadata inspection and a tiny conversion fixture pass; it is `needs-review` when custom code, missing files, or an untested architecture is involved. The matrix is documentation and test data, not a promise that every checkpoint in a family works.

Definitions used in the CLI and report:

- **Fit:** estimated inference weights plus KV cache stay below the model budget after the configured reserve; temporary conversion disk is checked separately.
- **Safe automatic plan:** a plan selected by policy with known metadata and no unresolved compatibility or disk warning.
- **Supported:** a named architecture and checkpoint shape passed preflight and a tiny conversion fixture.
- **Risky:** a model requiring custom code, incomplete metadata, unmeasured conversion behavior, or an estimate that cannot be separated from peak conversion memory. The first release rejects these cases.
- **Verified:** tokenizer and model load succeeded, generation produced non-empty output, and the result plus any available peak-memory measurement was written to the report. This is a smoke test, not a quality or performance guarantee.

Benchmarking is a planned extension of the decision engine, not a first-release requirement. Later, a benchmark candidate can be converted and measured through the same stage interface, then selected using an explicit objective such as fastest generation under the memory budget.

The first-release cut is: one command, preflight confirmation, one selected automatic plan, fitting-only `--bits` overrides, early compatibility and disk checks, conversion, smoke verification, stable report schema version `1`, and support fixtures for the named architecture families. It excludes benchmark selection, model upload, a public plugin API, multimodal conversion, arbitrary remote-code execution, unsafe overrides, and reproducible-build commands.

## Open Questions

- The first conversion command pauses after preflight; `--yes` bypasses the pause for scripts and still records the plan.
- The support matrix requires one Llama and one Qwen-family fixture. Full Qwen conversion may run in scheduled or release CI if needed.
- Failed conversion and verification remove incomplete tensor output by default while retaining a diagnostic report.
- What exact runtime metric should define “fastest” when benchmark selection is added: prompt processing, generated tokens per second, peak memory, or a weighted combination?
- Report schema version `1` is recorded immediately and is explicitly experimental; until compatibility guarantees are published, consumers must reject unknown major schema versions and tolerate additive fields.

## Success Criteria

- A beginner can run one documented command with a Hugging Face model ID and produce a verified MLX model without manually selecting a bit-width.
- Preflight downloads zero weight bytes and reports the selected plan, expected model size, KV-cache estimate, available budget, estimated temporary disk, and the reason for the choice before weight download begins.
- Unsupported or missing metadata failures occur before the full checkpoint download whenever possible and identify a useful next action.
- A successful output contains a runnable MLX model and a schema-versioned report recording the resolved source revision, decision assumptions, conversion settings, disk estimate, and verification result.
- Tests cover decision-engine policy, architecture eligibility, metadata-estimate provenance, conversion-stage boundaries, report schema, and verification failures without requiring large model downloads.
- macOS integration CI continues to convert and verify a tiny Llama checkpoint, includes Qwen-family coverage in scheduled or release CI if needed, and exercises an early unsupported-model failure on every PR.
- README examples describe the beginner path first and clearly distinguish estimated fit from measured performance.
- A reference 32 GB Apple Silicon run reaches a successful verified output with no unexplained decision, and records setup time, download size, conversion duration, and peak memory when available.
- Disk-space, revision pinning, private/gated model authentication, network interruption, cancellation, and failed-conversion cleanup each have a defined user-visible result and a test.

## Distribution Plan

Distribution remains the existing PyPI package at `mlx-autoquant`, installed with `pip install mlx-autoquant`. GitHub Actions continues to run lint, formatting, type checks, unit tests, and macOS integration tests. Version tags build and publish distributions through the existing release workflow. The first release of the decision engine should include updated README examples and a support-matrix document so users can understand the boundary before trying a large model.

## Engineering Review Outputs

### What Already Exists

- `src/mlx_autoquant/planner.py` already models hardware budget, KV cache, candidate bit-widths, fit status, and rationale. The decision engine should extend these types instead of replacing the memory policy.
- `src/mlx_autoquant/model.py` already profiles `config.json` and records exact versus estimated parameter counts. The new preflight should preserve that provenance while rejecting incomplete architecture data instead of silently defaulting it.
- `src/mlx_autoquant/verify.py` already loads a converted model, generates text, and records peak memory when available. The verification stage should extend this result with explicit load and generation statuses.
- `src/mlx_autoquant/cli.py` already owns the public command, progress output, output-directory guard, and JSON mode. The new modules should move policy and side effects behind it rather than create a second entry point.
- `.github/workflows/ci.yml` already runs macOS unit and integration checks, and `.github/workflows/release.yml` already publishes the PyPI package. No new distribution artifact is needed.

### NOT in scope

- Benchmark-based quantization selection: deferred to `TODOS.md` until conversion safety and report data are proven.
- Reproducible build inspection and replay commands: deferred to `TODOS.md` until the first report schema and transaction layout stabilize.
- Multimodal checkpoints, arbitrary remote code, model uploads, and a public plugin/frontend API: outside the first-release boundary.
- Parallel downloads: selective snapshot reuse is the first performance change; concurrency requires measured evidence.

| Failure | Test | Error handling | User-visible result |
| --- | --- | --- | --- |

### Decisions Made

- Use one pinned local snapshot as the source of truth.
- Use a versioned support matrix backed by conversion fixtures.
- Bound `mlx-lm` and advance compatibility through tested releases.
- Split internal stages into focused modules; do not create a public plugin API.
- Use typed error categories.
- Use layered tests and release-blocking failure cleanup coverage.
- Use selective snapshot reuse, not parallel downloads, in the first release.
- Measure conversion envelopes before promising safe fit.
- Probe the converter API and validate the real Qwen3 27B scenario before refactoring.
- Use a sibling transaction directory and promote only verified output.
- Defer benchmark selection and reproducible build artifacts to `TODOS.md`.

### Reduced-Scope Review Decisions

- Bound `mlx-lm` to a tested compatibility range in the first slice.
- Resolve a required-file manifest before downloading the pinned local snapshot.
- Resolve the immutable Hub commit once and use it for all metadata, cache, snapshot, and conversion operations.
- Write and flush the success report before atomically promoting output.
- Keep `--no-verify` only as an explicit unverified promotion path with `verification.skipped` status.
- Remove `--trust-remote-code` from the first release.
- Separate small Qwen architecture support from large Qwen3 27B hardware-fit validation.
- Use one explicit Hugging Face cache root plus sibling transaction staging and count reusable files by resolved revision.
